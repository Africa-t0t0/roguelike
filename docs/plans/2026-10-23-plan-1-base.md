# Plan 1: Base co-op (mazmorra + movimiento en red). Plan de implementación

> **Para agentes:** SUB-SKILL REQUERIDA: usar superpowers:subagent-driven-development (recomendado) o superpowers:executing-plans para implementar este plan tarea por tarea. Los pasos usan checkboxes (`- [ ]`) para seguimiento.

**Objetivo:** Entre 1 y 4 jugadores, cada uno desde su casa, entran con un código de sala y un nombre a una mazmorra 3D generada por semilla. Se mueven y esquivan en tercera persona con predicción, ven a los demás interpolados, y si se desconectan vuelven a entrar con su nombre. Todo desplegado en un servidor accesible por internet.

**Arquitectura:** Monorepo con npm workspaces y tres paquetes: `shared` (lógica determinista: RNG, generador de mazmorras, movimiento y colisión), `server` (Colyseus autoritativo) y `client` (Babylon.js + Vite). El servidor manda solo la semilla y el número de piso, y cada cliente regenera la misma mazmorra. El movimiento corre la **misma función** `stepPlayer` en el servidor y en el cliente, y con eso se hace la predicción con reconciliación.

**Stack:** Node ≥ 24, TypeScript 7.0.2, Colyseus 0.18.9 (`colyseus`, `@colyseus/schema` 5, `@colyseus/sdk` 0.18.5, `@colyseus/testing` 0.18.x), Babylon.js 9.30.0 (`@babylonjs/core`), Vite 8.3.4, Vitest 5.0.3, tsx 4.x, concurrently 9.x.

**Spec:** `docs/specs/2026-10-23-roguelike-coop-design.md`. Este plan cubre los pasos 1 y 2 de la sección 6 del spec, más la identidad y reconexión de la sección 4.7 y el despliegue de la sección 5.1. Ver "Planes siguientes" al final.

## Restricciones globales

- Versiones exactas (publicadas hace ≥ 2 semanas): `@babylonjs/core@9.30.0`, `colyseus@0.18.9`, `@colyseus/sdk@0.18.5`, `vite@8.3.4`, `vitest@5.0.3`, `typescript@7.0.2`.
- Schemas de Colyseus con el builder `schema({...})` de `@colyseus/schema`, **sin decoradores**.
- Todo lo determinista (RNG, mazmorra, movimiento) vive en `shared` y **no usa `Math.random`**. Recibe un `Rng` o una semilla.
- Constantes (en `packages/shared/src/constants.ts`, una sola fuente de verdad):
  `SIM_HZ = 30`, `SIM_DT = 1 / SIM_HZ`, `PATCH_RATE_MS = 50`, `INTERP_DELAY_MS = 100`, `MAX_INPUTS_PER_TICK = 3`, `MAX_QUEUED_INPUTS = 30`, `MAX_PENDING_INPUTS = 90`, `TILE_SIZE = 2` (metros), `PLAYER_RADIUS = 0.4`, `PLAYER_SPEED = 5` (m/s), `DODGE_SPEED = 12` (m/s), `DODGE_DURATION = 0.25` (s), `DODGE_COOLDOWN = 1.0` (s), `MAX_PLAYERS = 4`, `EMPTY_ROOM_TTL_MS = 600_000`, `NAME_MAX_LEN = 16`, `ROOM_CODE_LENGTH = 5`, `ROOM_CODE_ALPHABET = "ABCDEFGHJKMNPQRSTUVWXYZ23456789"`.
- Ejes: el mundo es el plano XZ con Y hacia arriba. `facing` es el ángulo en radianes donde 0 apunta a +Z y π/2 a +X. Las coordenadas de mundo están en metros, y la casilla `(tx, tz)` cubre `[tx*TILE_SIZE, (tx+1)*TILE_SIZE)`.
- Textos visibles al usuario en **español**. Identificadores de código en inglés.
- Commits terminan con `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- Gráficos de este plan: **primitivas** (cajas para muros, cápsulas con el nombre encima para jugadores). Los assets reales (KayKit/Mixamo) entran en el Plan 2, junto con las animaciones. Así este plan valida la red sin depender del arte.

## Foco de revisión

1. **Mismo nombre con distinta forma** (`"Jorge"`, `" jorge "`, `"JORGE"`): son el mismo jugador. Se compara por la clave normalizada y se muestra el nombre tal como se escribió la primera vez. Test en la Tarea 4.
2. **Recargar la pestaña a mitad de run**, antes de que el servidor note que se cayó la conexión anterior: el jugador debe recuperar su personaje, no recibir "nombre en uso". Se resuelve con un token por navegador (en `localStorage`), y mismo nombre + mismo token = toma el control. Tests en las Tareas 4 y 5.
3. **Código de sala inexistente o mal escrito**: el lobby muestra "No existe una sala con ese código" y deja reintentar, sin pantalla rota. El test del servidor va en la Tarea 5 y el mapeo del error a texto en la Tarea 7.
4. **Ráfaga de inputs** (pestaña en segundo plano que al volver manda muchos inputs juntos): el servidor procesa como máximo `MAX_INPUTS_PER_TICK` por tick y descarta los más viejos sobre `MAX_QUEUED_INPUTS`, así nadie se teletransporta ni corre más rápido. Test en la Tarea 5.
5. **La ventana pierde el foco con una tecla apretada** (alt-tab o `Esc` que suelta el puntero): el personaje no debe seguir caminando solo. `blur` suelta todas las teclas. Test en la Tarea 7.

### Tarea 2: Generador de mazmorras

**Archivos:**
- Crear: `packages/shared/src/dungeon.ts`
- Test: `packages/shared/test/dungeon.test.ts`

**Interfaces:**
- Consume: `createRng`, `TILE_SIZE`.
- Produce:
  ```ts
  type RoomKind = "start" | "combat" | "boss";
  interface DungeonRoom { id: number; x: number; z: number; w: number; h: number; kind: RoomKind; neighbors: number[] }
  interface Dungeon { seed: number; floor: number; width: number; height: number; tiles: Uint8Array /* 0 muro, 1 suelo; índice z*width+x */; rooms: DungeonRoom[]; startRoomId: number; bossRoomId: number }
  generateDungeon(seed: number, floor: number): Dungeon
  isWalkableTile(d: Dungeon, tx: number, tz: number): boolean   // false fuera de rango
  tileCenter(tx: number, tz: number): { x: number; z: number }  // en metros
  roomSpawnPoints(d: Dungeon, roomId: number, count: number): { x: number; z: number }[]  // centros de casillas de suelo distintas dentro de la sala
  ```

Reglas: `rooms.length = 6 + 2 * floor`. Cada sala mide entre 5 y 9 casillas por lado y entre salas queda un margen de al menos 2 casillas de muro. La grilla mide `width = height = 40 + 8 * floor`, y el borde exterior es siempre muro. Las salas se colocan por rechazo con el RNG; si no caben en 500 intentos, la grilla crece 8 casillas y se reintenta. Las salas se conectan con un árbol de expansión mínima (Prim sobre los centros) más **una** arista extra al azar para formar un ciclo. Los pasillos tienen forma de L y miden 1 casilla de ancho. `neighbors` refleja esas aristas. La sala `start` es `rooms[0]`, y `boss` es la sala con mayor distancia BFS desde `start` en el grafo de salas (si hay empate, gana el id menor). El resto son `combat`.

### Tarea 3: Movimiento, esquive y colisión

**Archivos:**
- Crear: `packages/shared/src/movement.ts`
- Test: `packages/shared/test/movement.test.ts`

**Interfaces:**
- Consume: `Dungeon`, `isWalkableTile`, constantes de movimiento.
- Produce:
  ```ts
  interface KinematicState { x: number; z: number; facing: number; dodgeTime: number /* s restantes */; dodgeCooldown: number; dodgeDirX: number; dodgeDirZ: number }
  interface PlayerInput { seq: number; moveX: number; moveZ: number; facing: number; dodge: boolean }
  sanitizeInput(raw: unknown): PlayerInput | null   // null si no es objeto o seq no es entero ≥ 0; NaN/Infinity → 0; |move| > 1 → normalizado; dodge !== true → false
  stepPlayer(s: KinematicState, input: PlayerInput, d: Dungeon, dt: number): KinematicState   // pura, no muta s
  isInvulnerable(s: KinematicState): boolean        // dodgeTime > 0
  ```

Reglas: si `input.dodge` llega con `dodgeCooldown <= 0`, `dodgeTime > 0` no ocurre nada nuevo, y el movimiento no es cero, empieza un esquive en la dirección del movimiento. Durante el esquive la velocidad es `DODGE_SPEED` en esa dirección y se ignora el input de movimiento. En el paso donde termina el esquive solo se avanza durante el tiempo que le quedaba (`min(dt, dodgeTime)`), sin movimiento normal en el resto de ese paso, para que el esquive recorra exactamente `DODGE_SPEED * DODGE_DURATION`. Al empezar, `dodgeCooldown = DODGE_COOLDOWN`. Los timers bajan `dt` por paso y nunca quedan negativos. La colisión resuelve un círculo de radio `PLAYER_RADIUS` contra casillas de muro, primero en X y después en Z (eso hace que deslice por las paredes). `facing` se toma del input, salvo durante el esquive.

- [ ] **Paso 1: Tests que fallan** (sobre una `Dungeon` armada a mano en el test: una sala abierta de 10×10 casillas rodeada de muro):
  - 30 pasos con `moveX=1` desde el centro avanzan `x` en `PLAYER_SPEED * 1s` (±1e-6).
  - Con `moveX=1, moveZ=1`, la distancia recorrida en 1 s es `PLAYER_SPEED` (±1e-6), porque el movimiento diagonal se normaliza.
  - Caminar hacia +X durante 10 s deja a `x` exactamente en `bordeDelMuro - PLAYER_RADIUS` (±1e-6).
  - Caminar en diagonal contra el muro de +X sigue avanzando en Z (desliza).
  - Esquivar con `moveX=1` y después dar 8 pasos con movimiento 0 recorre exactamente `DODGE_SPEED * DODGE_DURATION` = 3 m (±1e-6). Como 0,25 s no es múltiplo de `SIM_DT`, esto prueba el último paso parcial. `isInvulnerable` es true durante el esquive y false al terminar. Un segundo `dodge` antes de que pase `DODGE_COOLDOWN` no hace nada.
  - `sanitizeInput({seq: 1, moveX: NaN, moveZ: 5, facing: 0, dodge: "yes"})` devuelve `{seq: 1, moveX: 0, moveZ: 1, facing: 0, dodge: false}`. `sanitizeInput("x")` y `sanitizeInput({seq: -1})` devuelven null.
  - `stepPlayer` no muta su argumento (comparar contra un `structuredClone`).

### Tarea 4: Registro de jugadores (identidad y reconexión)

**Archivos:**
- Crear: `packages/shared/src/protocol.ts`, `packages/server/src/rooms/PlayerRegistry.ts`
- Test: `packages/server/test/PlayerRegistry.test.ts`

**Interfaces:**
- Consume: `KinematicState`, `MAX_PLAYERS`, `NAME_MAX_LEN`.
- Produce, en `protocol.ts`:
  ```ts
  interface JoinOptions { name: string; token: string }
  type JoinErrorCode = "invalid-name" | "name-taken" | "room-full"
  const JOIN_ERROR_STATUS: Record<JoinErrorCode, number> = { "invalid-name": 4001, "name-taken": 4002, "room-full": 4003 }
  const MSG = { input: "input", welcome: "welcome" } as const   // welcome: { key: string }
  normalizeName(raw: unknown): { display: string; key: string } | null   // trim, espacios internos colapsados, 1..NAME_MAX_LEN caracteres de [\p{L}\p{N} _-]; key = display en minúsculas
  ```
  En `PlayerRegistry.ts`:
  ```ts
  interface PlayerRecord { key: string; displayName: string; token: string; sessionId: string | null; kinematic: KinematicState; lastSeq: number; inputQueue: PlayerInput[] }
  type JoinResult =
    | { ok: true; kind: "new" | "reconnect" | "takeover"; record: PlayerRecord; replacedSessionId?: string }
    | { ok: false; code: JoinErrorCode }
  class PlayerRegistry {
    constructor(maxPlayers?: number)
    join(opts: { name: unknown; token: unknown; sessionId: string }, spawn: () => KinematicState): JoinResult
    leave(sessionId: string): PlayerRecord | undefined   // deja sessionId = null, conserva el registro
    bySession(sessionId: string): PlayerRecord | undefined
    connected(): PlayerRecord[]
    size(): number                                        // conectados + desconectados
  }
  ```

Reglas: nombre inválido → `invalid-name`. Clave conectada + mismo token → `takeover`: se reemplaza el `sessionId`, se devuelve el anterior en `replacedSessionId` y se vacía `inputQueue`. Clave conectada + otro token → `name-taken`. Clave desconectada → `reconnect`, con cualquier token, que pasa a ser el nuevo. Clave nueva con `size() >= maxPlayers` → `room-full`. En `new`, `reconnect` y `takeover` se llama a `spawn()` para ubicar al personaje (el spec dice que al volver aparece junto a un aliado), y `lastSeq` vuelve a 0 para que la secuencia del cliente nuevo arranque de cero.

### Tarea 5: Sala de run en Colyseus

**Archivos:**

- Test: `packages/server/test/roomCode.test.ts`, `packages/server/test/RunRoom.test.ts`

**Interfaces:**
- Consume: `PlayerRegistry`, `generateDungeon`, `roomSpawnPoints`, `isWalkableTile`, `tileCenter`, `stepPlayer`, `sanitizeInput`, `MSG`, `JOIN_ERROR_STATUS`, constantes.
- Produce:
  - `createRoomCode(rng: Rng): string` (`ROOM_CODE_LENGTH` caracteres de `ROOM_CODE_ALPHABET`).
  - `PlayerState = schema({ name: "string", x: "number", z: "number", facing: "number", dodgeTime: "number", dodgeCooldown: "number", dodgeDirX: "number", dodgeDirZ: "number", lastSeq: "number" })`
  - `RunState = schema({ seed: "number", floor: "number", players: { map: PlayerState } })`, con `players` indexado por la **clave** del jugador, no por `sessionId`.
  - La sala se registra como `"run"`. Opciones de creación para tests: `{ seed?: number; emptyRoomTtlMs?: number }`.
  - `export const appConfig` en `app.config.ts`, que usan tanto `index.ts` (`listen(appConfig, PORT)`, con `PORT` por defecto 2567) como los tests (`boot(appConfig)`).

Comportamiento:
- `onCreate`: `this.roomId = createRoomCode(...)`. Si `matchMaker.query({ roomId })` ya encuentra una sala con ese código, se reintenta hasta 5 veces. Además: semilla al azar (o la de las opciones), piso 1, `autoDispose = false`, `setPatchRate(PATCH_RATE_MS)` y `setSimulationInterval(tick, 1000 / SIM_HZ)`.
- `onJoin`: llama a `registry.join`. Si falla, lanza `ServerError(JOIN_ERROR_STATUS[code], code)`. Si fue `takeover`, desconecta al cliente anterior. Agrega o actualiza `players[key]` y le envía `MSG.welcome` con `{ key }` solo a ese cliente. Spawn: si hay otro jugador conectado, la primera casilla caminable a ≤ 2 casillas de él que no esté ocupada; si no, `roomSpawnPoints(start)`. Cancela el temporizador de sala vacía.
- `onLeave` (en 0.18 también aplica `onDrop`; **no** se usa `allowReconnection`, porque la reconexión es por nombre): `registry.leave` y `players.delete(key)`. Si no quedan conectados, a los `emptyRoomTtlMs` (por defecto `EMPTY_ROOM_TTL_MS`) llama a `this.disconnect()`.
- Mensaje `MSG.input`: aplica `sanitizeInput`, descarta el input si `seq <= lastSeq` o si ya está en cola, lo encola y descarta los más viejos sobre `MAX_QUEUED_INPUTS`.
- `tick`: por cada jugador conectado procesa hasta `MAX_INPUTS_PER_TICK` inputs de la cola, cada uno con `stepPlayer(…, SIM_DT)`, actualiza `lastSeq` y copia el `KinematicState` al `PlayerState`. Si un tick no tiene inputs, el jugador no avanza (el servidor solo simula sobre inputs recibidos, igual que el cliente).

### Tarea 6: Red del cliente: simulador de retraso, predicción e interpolación

**Archivos:**
- Crear: `packages/client/src/net/{LagSimulator.ts,Predictor.ts,SnapshotBuffer.ts}`
- Test: `packages/client/test/{LagSimulator,Predictor,SnapshotBuffer}.test.ts`

**Interfaces:**
- Consume: `stepPlayer`, `KinematicState`, `PlayerInput`, `Dungeon`, `createRng`, `SIM_DT`, `MAX_PENDING_INPUTS`.
- Produce:
  ```ts
  interface LagConfig { delayMs: number; jitterMs: number; loss: number }
  parseLagParams(search: string): LagConfig          // ?lag=150&jitter=20&loss=0.02 ; todo 0 si falta o es inválido; loss acotado a [0, 0.5]
  class LagSimulator {
    constructor(cfg: LagConfig, rng?: Rng)
    outbound(send: () => void): void                 // puede descartar (loss) y retrasa delay/2 ± jitter/2
    inbound(deliver: () => void): void               // nunca descarta; retrasa delay/2 ± jitter/2
  }
  class Predictor {
    constructor(initial: KinematicState, dungeon: Dungeon)
    applyLocal(input: PlayerInput): KinematicState   // avanza un SIM_DT y guarda el input como pendiente
    reconcile(server: KinematicState, ackSeq: number): KinematicState   // descarta pendientes con seq ≤ ack y re-simula los restantes
    get current(): KinematicState
    get pendingCount(): number
  }
  class SnapshotBuffer<T> {
    constructor(lerp: (a: T, b: T, t: number) => T, keepMs?: number /* 1000 */)
    push(timeMs: number, snap: T): void
    sample(renderTimeMs: number): T | undefined     // interpola entre los dos que rodean; antes del primero → primero; después del último → último (sin extrapolar)
  }
  ```

Reglas: con `delayMs = 0` el LagSimulator ejecuta las funciones de inmediato y en forma síncrona. Con retraso **mantiene el orden** de cada dirección: el tiempo programado de cada envío nunca es menor que el del envío anterior, porque WebSocket entrega en orden. Si los pendientes del Predictor superan `MAX_PENDING_INPUTS`, se descartan los más viejos.

  - Con jitter de 80, 50 envíos se ejecutan en el mismo orden en que se programaron.

  ```ts
  // InputState.ts: lógica pura, sin DOM
  class InputState {
    keyDown(code: string): void; keyUp(code: string): void; blur(): void

  ```

Convención de cámara: con `cameraYaw = 0` la cámara mira hacia +Z, así que W da `(moveX, moveZ) = (sin yaw, cos yaw)` y D da `(cos yaw, -sin yaw)`. `facing` = `cameraYaw` mientras haya movimiento, y si no se conserva el último.

Comportamiento:
- **Lobby** (HTML simple sobre el canvas): un campo "Tu nombre" (se recuerda en `localStorage`), un botón "Crear sala" y un campo de código con botón "Unirse". El token se crea una vez con `crypto.randomUUID()` y se guarda en `localStorage`. Los errores se muestran con `joinErrorMessage`. En el juego, el código de sala queda visible en una esquina para compartirlo.
- **URL del servidor:** en desarrollo `ws://localhost:2567`, y en producción el mismo origen (`wss://` + `location.host`). Se elige con `import.meta.env.DEV`.
- **Bucle:** un acumulador de tiempo fijo con `SIM_DT`. En cada paso: `InputState.sample` → `Predictor.applyLocal` → `sendInput` (pasa por `LagSimulator.outbound`). Al llegar estado (pasa por `LagSimulator.inbound`): para mí, `Predictor.reconcile(server, lastSeq)`; para los demás, `SnapshotBuffer.push(receivedAt, …)`. Se dibuja a los demás en `now - INTERP_DELAY_MS`. Una corrección de la predicción mayor a 0,01 m se suaviza visualmente en ~100 ms; la lógica no se suaviza.
